数据库方案详解（通俗版）

三个方案的本质区别和选择建议

🔍 先理解当前问题
您的项目现状：
• 完全没有数据库，所有数据都存在文件里（JSON 和 Markdown）
• 这就像用记事本管理公司员工档案，虽然能用，但：
  ❌ 删除章节后，伏笔引用还在（数据不一致）
  ❌ 无法快速查询"哪些伏笔还没解决"（没有查询功能）
  ❌ 多个操作同时进行容易出错（没有并发保护）

核心矛盾：
• 需要数据库来管理"结构化数据"（用户、项目、章节列表、伏笔关系）
• 但您已经有自己实现的"向量搜索系统"（用于语义检索章节内容）
• 要决定：是完全替换成数据库，还是混合使用？

📦 方案A：渐进式混合（推荐）

核心思路：只把"该用数据库的"放数据库
第一阶段：把元数据迁移到 SQLite
什么是元数据？就是"数据的目录"，比如：
• 用户表：用户名、邮箱、密码
• 小说项目表：小说标题、作者、创建时间
• 章节表：章节标题、字数、状态
• 伏笔表：伏笔名称、在哪个章节埋下、在哪个章节解决

为什么用 SQLite？
SQLite 就是一个"文件版数据库"，不需要安装数据库软件，只需要一个 novelagent.db 文件。
就像 Excel 文件，双击就能打开，但比 Excel 强大一万倍。

第二阶段：保留现有优势
• ✓ 章节内容继续用 Markdown 文件存（方便版本控制，用 Git 管理）
• ✓ 向量索引继续用文件存（您的自研系统已经够用，1000 章以内性能很好）
• ✓ Embedding 继续用本地模型（不改动）
✅ 优点
• 解决核心痛点：删除章节后，数据库自动清理相关伏笔（外键约束）
• 支持复杂查询："查询所有未解决的伏笔"这种操作变得简单
• 开发快：2-3 周完成
• 零配置：不需要安装额外软件
• 风险低：保留现有优势，只改必须改的
⚠️ 局限
• SQLite 并发写入能力有限（同时只能一个人写入）
• 适合中小规模（<10,000 用户）
• 如果以后用户量暴增，需要迁移到 PostgreSQL（但很容易迁移）
适合场景：
• 你现在的情况（需要多用户系统，但用户量不会很大）
• 想快速上线验证产品（2-3 周 vs 4-6 周）
• 不想维护复杂的数据库服务
• 以后可以无缝升级到 PostgreSQL（.NET 的 EF Core 支持平滑迁移）

🚀 方案B：PostgreSQL + pgvector（一步到位）

核心思路：用工业级数据库全面替换
全面升级：
• 所有结构化数据 → PostgreSQL（比 SQLite 强大得多）
• 向量数据也迁移 → pgvector 扩展（PostgreSQL 的向量搜索插件）
• 用 HNSW 索引（一种高效的向量检索算法）

PostgreSQL 是什么？
世界上最先进的开源数据库之一，互联网大公司都在用。
支持高并发（成千上万人同时访问不会卡）、支持复杂查询、生产级稳定性。

pgvector 是什么？
PostgreSQL 的一个扩展，专门用来存储和检索向量数据。
可以替代您自己实现的文件向量索引。
✅ 优点
• 性能天花板高：可以支持百万级用户
• 并发能力强：成千上万人同时使用不会卡
• 功能丰富：支持全文搜索、地理数据、JSON 查询等
• 一劳永逸：不需要再升级数据库
⚠️ 代价
• 需要安装 PostgreSQL（一个独立的数据库服务）
• 运维复杂：要监控、备份、优化性能
• 开发慢：4-6 周（数据迁移 + 向量索引重构）
• 资源消耗大：PostgreSQL 比 SQLite 吃内存
适合场景：
• 你明确知道会有大量用户（>10,000 人）
• 对性能和并发有极高要求
• 有专业运维人员或愿意学习数据库运维
• 章节数会超过 2000 章，向量检索成为瓶颈

问题：你现在用户量不大，章节数也不多，用这个方案有点"杀鸡用牛刀"。

🔗 方案C：SQLite + 外部向量数据库

核心思路：结构化数据用 SQLite，向量数据用专业工具
混合架构：
• 结构化数据（用户、项目、章节列表）→ SQLite
• 向量数据（Embedding、语义检索）→ Qdrant 或 Milvus（专业向量数据库）

Qdrant/Milvus 是什么？
专门为 AI 应用设计的向量数据库，比自己实现的文件索引性能好得多。
支持高效的相似度搜索、过滤、聚合等操作。
可以用 Docker 一键部署。
✅ 优点
• 术业有专攻：向量检索比方案A快很多
• 支持高级功能：混合搜索、过滤、聚合
• 可扩展性好：向量数据可以独立扩展
• 保持简单：结构化数据还是 SQLite（不需要 PostgreSQL）
⚠️ 问题
• 架构复杂：要维护两套系统（SQLite + 向量数据库）
• 需要 Docker：向量数据库要跑在容器里
• 当前不需要：你的文件向量索引性能还不错（<100ms）
• 增加成本：多一个服务就多一份维护负担
适合场景：
• 向量检索变慢了（延迟 >200ms）
• 章节数超过 1000 章
• 需要复杂的向量过滤和聚合功能

问题：你现在还没到这个阶段，引入专业向量数据库是"过度设计"。

🎯 我的推荐：选方案A

为什么推荐A？

1️⃣ 解决核心问题：引用完整性（删除章节自动清理伏笔）、结构化查询、并发安全
2️⃣ 开发快：2-3 周 vs 4-6 周，能更快验证多用户系统是否好用
3️⃣ 零配置：SQLite 是一个文件，不需要安装数据库软件
4️⃣ 保留优势：你的向量索引系统继续用，Markdown 文件继续用，不推倒重来
5️⃣ 可升级：以后用户量大了，可以无缝升级到 PostgreSQL（.NET 支持）

方案B什么时候选？
• 你已经有 1 万以上用户
• 并发写入成为瓶颈（多人同时编辑卡顿）
• 章节数超过 2000，向量检索变慢

方案C什么时候选？
• 向量检索延迟超过 200ms
• 需要复杂的向量过滤（比如"找出所有包含'修仙'和'战斗'场景的章节"）

现在的情况：方案A最合适，快速上线，遇到瓶颈再升级。

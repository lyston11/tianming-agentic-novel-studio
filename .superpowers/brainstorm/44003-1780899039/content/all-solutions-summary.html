⏳ 第五决策：数据库架构方案（待选择）

🎯 核心发现
✓ 项目未使用任何数据库，纯文件系统存储（JSON + Markdown）
✓ 已实现自研向量索引（int8 量化，三层检索）
✓ 本地 Embedding（bge-small-zh-v1.5，512维）
✓ 最大痛点：数据完整性缺失（删除章节后伏笔引用仍存在）
✓ 性能瓶颈：Story Bible 单文件 52K+ tokens
方案A：渐进式混合（推荐）
Phase 1: 元数据迁移 SQLite（users, projects, chapters, foreshadows, characters）
Phase 2: 保留现有优势（章节内容 Markdown、向量索引文件存储）

✓ 解决引用完整性（外键约束）
✓ 支持结构化查询
✓ 零配置部署（SQLite 单文件）
✓ 开发周期：2-3周
方案B：PostgreSQL + pgvector（一步到位）
全面升级：所有数据 → PostgreSQL，向量 → pgvector（HNSW 索引）

✓ 生产级性能、高并发支持
✗ 需要部署 PostgreSQL 服务
✗ 运维复杂度高
✗ 开发周期：4-6周

适用场景：章节数 >2000 或高并发需求
方案C：SQLite + 外部向量数据库
混合架构：结构化数据 → SQLite，向量 → Qdrant/Milvus（Docker）

⚠️ 当前文件向量索引性能尚可（<100ms）
⚠️ 引入外部服务增加复杂度

时机：向量检索延迟 >200ms 或章节数 >1000 时再考虑
